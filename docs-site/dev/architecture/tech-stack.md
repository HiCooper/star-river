# 技术选型依据

## 选型原则

| 原则 | 说明 |
|------|------|
| **团队优先** | 选团队熟悉的，降低学习成本和风险 |
| **足够就好** | 不过度设计，满足当前规模需求 |
| **生态成熟** | 社区活跃，工具链完善，遇到问题能解决 |
| **可演进** | 预留升级空间，不锁死未来 |

---

## 1. 后端语言: Go

| 考量维度 | 分析 | 结论 |
|----------|------|------|
| **团队技能** | 团队熟悉 Go | ✅ 无学习成本 |
| **性能** | 编译型语言，单机 QPS 10k+ | ✅ 高性能 |
| **并发模型** | goroutine + channel，天然支持高并发 | ✅ 适合 SDK 频繁请求 |
| **启动速度** | 编译后二进制，秒级启动 | ✅ 适合容器化 |
| **生态** | net/http, gin, gorm 成熟 | ✅ 工具链完善 |
| **对比 Rust** | 性能相当，但学习曲线陡峭 | ✅ Go 更适合团队 |
| **对比 Java** | 性能相近，但内存占用高、启动慢 | ✅ Go 更轻量 |

**为什么不用 Java/Node.js/Python?**

| 语言 | 问题 |
|------|------|
| Java | 内存占用大 (~512MB)，启动慢 |
| Node.js | 单线程，CPU 密集型任务弱 |
| Python | 性能最弱，不适合高并发 |

## 2. 后端框架: Gin

| 考量维度 | 分析 | 结论 |
|----------|------|------|
| **性能** | 相比 Echo/Fiber，middleware 性能略低但足够 | ✅ 满足需求 |
| **生态** | 中间件丰富 (auth, cors, ratelimit) | ✅ 开箱即用 |
| **团队熟悉度** | 团队用过 | ✅ 无学习成本 |
| **对比 Echo** | 功能相似，Gin middleware 更丰富 | ✅ 选 Gin |
| **对比 Fiber** | 基于 fasthttp，性能更高，但生态较新 | ➖ 稳定性优先 |

---

## 3. 数据库: PostgreSQL

| 考量维度 | 分析 | 结论 |
|----------|------|------|
| **事务支持** | ACID 完整事务，支付场景必须 | ✅ |
| **JSONB** | paywall config/rules 用 JSONB 存储，灵活查询 | ✅ |
| **JSON 索引** | 可对 JSON 字段建 GIN 索引 | ✅ |
| **丰富类型** | Array, HStore, Range types | ✅ |
| **对比 MySQL** | JSON 支持更好，CTE 递归查询更强 | ✅ 选 PG |
| **对比 MongoDB** | 关系型数据 JOIN 更方便 | ✅ 选 PG |
| **对比 TiDB** | 分布式能力，但运维复杂 | ➖ 当前规模不需要 |

**为什么支付数据用 PostgreSQL 而不是 MongoDB?**

| 需求 | PostgreSQL | MongoDB |
|------|-----------|---------|
| 强一致性 | ✅ ACID 完整 | ⚠️ 需要配置副本集 |
| 复杂查询 | ✅ 多表 JOIN | ❌ 聚合管道复杂 |
| 事务保证 | ✅ 原生支持 | ⚠️ 分布式事务复杂 |
| 团队熟悉度 | ✅ 更熟悉 | ❌ |

## 4. 分析数据库: ClickHouse

| 考量维度 | 分析 | 结论 |
|----------|------|------|
| **OLAP 性能** | 列式存储，压缩率高 (10x+)，聚合查询快 100x | ✅ |
| **实时写入** | 支持近实时写入，秒级延迟 | ✅ |
| **SQL 支持** | 兼容标准 SQL，学习成本低 | ✅ |
| **对比 Elasticsearch** | ES 更适合搜索，AP 查询不如 CK | ✅ 选 CK |
| **对比 Druid** | 实时性不如 CK | ✅ 选 CK |
| **对比 StarRocks** | 较新，生态不如 CK | ➖ 保守选 CK |

**ClickHouse 适用场景示例:**

```sql
-- 用户事件分析 (千万级数据，秒级返回)
SELECT 
    paywall_id,
    count() as views,
    sum(is_converted) as conversions,
    conversions / views as cvr
FROM user_events
WHERE event_date >= today() - 7
GROUP BY paywall_id
ORDER BY cvr DESC
```

## 5. 缓存: Redis

| 考量维度 | 分析 | 结论 |
|----------|------|------|
| **性能** | 单机 10万+ QPS，微妙级延迟 | ✅ |
| **数据结构** | String/Hash/List/Set/ZSet 丰富 | ✅ |
| **过期策略** | TTL 支持，entitlement 缓存天然适合 | ✅ |
| **分布式锁** | RedLock 支持 | ✅ |
| **对比 Memcached** | Redis 数据结构更丰富 | ✅ 选 Redis |
| **对比 Dragonfly** | 太新，生产案例少 | ➖ 稳定性优先 |

**Redis vs Memcached 对比:**

| 特性 | Redis | Memcached |
|------|-------|-----------|
| 持久化 | ✅ 支持 | ❌ |
| 数据结构 | 丰富 (5种) | 仅 String |
| 集群 | Cluster 模式 | 客户端分片 |
| 内存效率 | 略低 | 略高 |
| **结论** | 功能更重要 | - |

## 6. 消息队列: Kafka

| 考量维度 | 分析 | 结论 |
|----------|------|------|
| **吞吐量** | 百万级 QPS | ✅ |
| **持久化** | 磁盘持久化，消息不丢 | ✅ |
| **多消费者** | Topic/Consumer Group 灵活 | ✅ |
| **事件溯源** | 付费事件需要可追溯 | ✅ |
| **对比 RabbitMQ** | 吞吐量差一个数量级 | ✅ 选 Kafka |
| **对比 RocketMQ** | 阿里系，团队不熟悉 | ➖ |
| **对比 Pulsar** | 较新，生态不如 Kafka | ➖ |

**为什么不用 RabbitMQ?**

| 场景 | RabbitMQ | Kafka |
|------|----------|-------|
| 吞吐量 | 万级 QPS | 百万级 QPS |
| 持久化 | 可选 | 默认持久化 |
| 适用场景 | 微服务 RPC | 事件流 |
| **结论** | 适合内部通信 | 适合高吞吐事件 |

**付费场景特殊需求:**
- 高峰期可能瞬间百万事件 (活动推广)
- 需要保留原始事件供回溯分析
- 多个下游消费 (分析、审计、通知)

## 架构决策记录 (ADR)

### ADR-001: 采用独立数据库而非共享数据库

**决策:** hydra-wall 和 hydra-pay 使用独立的 PostgreSQL 数据库。

**原因:**
- 两个服务有不同的一致性要求 (支付服务需要更强的事务保证)
- 可独立扩缩容和备份
- 故障隔离，一个服务不影响另一个
- 团队可以独立开发和部署

**替代方案:**
- 共享数据库: 简单但耦合度高
- 分库分表: 过度设计，当前规模不需要

### ADR-002: 采用 Webhook 而非同步调用进行状态同步

**决策:** hydra-pay 通过 Webhook 异步通知 hydra-wall 支付结果。

**原因:**
- 解耦两个服务，hydra-pay 不需要知道 hydra-wall 的存在
- 异步处理不影响支付主流程
- 重试机制保证最终一致性
- hydra-wall 可以批量处理更新

**替代方案:**
- 同步 RPC: 简单但耦合度高，支付服务受影响
- 消息队列: 过度设计，webhook 足够

### ADR-003: 支付路由采用服务端计算

**决策:** 支付路由逻辑在 hydra-pay 服务端计算，不下发给客户端。

**原因:**
- 安全: 渠道选择逻辑不能被客户端操控
- 灵活性: 可以随时调整路由策略无需更新客户端
- 可见性: 服务端可以记录完整的路由决策日志

**替代方案:**
- 客户端选择: 存在安全隐患，可能被滥用

### ADR-004: 付费墙配置通过 SDK 本地缓存

**决策:** SDK 本地缓存付费墙配置，减少服务端请求。

**原因:**
- 降低延迟: 本地读取 < 1ms
- 减轻服务端压力: 大部分请求可本地处理
- 离线可用: 配置可离线缓存

**替代方案:**
- 每次请求服务端: 延迟高，服务压力大
