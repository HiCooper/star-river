# 自动修复工作流

星河哨兵支持对低风险 Issue 自动生成代码修复并提交 PR。本文档详细介绍自动修复的完整流程和决策逻辑。

## 触发条件

自动修复仅在以下条件**全部满足**时触发：

```
✅ AI 评估 auto_fixable = yes
✅ 严重性 severity ∈ {low, medium}
✅ 通过 6 层安全边界检查
✅ 变更范围 ≤ 50 行 且 ≤ 3 个文件
✅ 路径不在全局/服务级黑名单中
✅ 代码不含黑名单关键词
✅ AI 置信度 ≥ 60%
```

任一条件不满足 → 路由到人工审批流程。

## 完整流程

```
┌─────────────────────────────────────────────────────────┐
│  1. Issue 触发自动修复                                    │
│     → 查询 Issue 详情 (错误堆栈、AI 分析结果)              │
│     → 查询 sentinel.yaml (repo、fix pipeline 配置)        │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│  2. 安全检查 (一票否决)                                   │
│     → 检查 6 层安全边界                                   │
│     → 失败 → 降级到人工审批 + 记录原因                     │
└────────────────────┬────────────────────────────────────┘
                     ↓ (通过)
┌─────────────────────────────────────────────────────────┐
│  3. 环境准备                                             │
│     → git clone <repo_url>                               │
│     → git checkout -b sentinel/auto-fix-{issue_id}       │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│  4. Claude Code CLI 生成修复                              │
│     → 输入: 错误堆栈 + 源码上下文 + AI 修复建议            │
│     → claude -p "修复 bug: ..." --allowedTools ...         │
│     → 输出: 代码补丁 (diff)                                │
│     → 保存 diff 到 MinIO (审计)                           │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│  5. 运行测试验证                                         │
│     → go test ./... (或其他语言测试命令)                   │
│     → lint check                                         │
│     → build check                                        │
└────────┬──────────────────────────┬─────────────────────┘
         ↓ (全部通过)               ↓ (失败)
┌────────────────────┐   ┌────────────────────────────────┐
│  6a. 提交 & 创建 PR │   │  6b. 重试 (最多 2 次)           │
│  git add .         │   │  → 将失败日志作为上下文          │
│  git commit        │   │  → 重新调用 Claude Code CLI     │
│  git push          │   │  → 仍失败 → 降级人工审批         │
│  gh pr create      │   └────────────────────────────────┘
└────────┬───────────┘
         ↓
┌─────────────────────────────────────────────────────────┐
│  7. 更新 Issue                                           │
│     → fix_type: auto                                     │
│     → fix_pr_url: <pr_link>                              │
│     → fix_status: pending_review                         │
│     → 写入 issue_timeline                                │
│     → 发送通知 (Slack/钉钉)                               │
└─────────────────────────────────────────────────────────┘
```

## PR 格式

自动生成的 PR 包含结构化描述：

```markdown
## 自动修复: {issue_title}

**Issue**: #{issue_id}
**服务**: {service_name}
**分类**: {category} | **严重性**: {severity}
**AI 置信度**: {confidence}%

### 错误摘要
{error_summary}

### 修复说明
{fix_explanation}

### 修改文件
- {file_1} (+{added} -{deleted})
- {file_2} ...

### 测试结果
{test_output_summary}

### AI 分析
- 推测原因: {root_cause}
- 修复策略: {fix_strategy}

---
> 此 PR 由星河哨兵 (Sentinel) 自动生成。
> 如需回退，请关闭此 PR 并在 Issue 中标记 `sentinel:revert`。
> 人工审核通过后使用 Squash Merge 合并。
```

## 重试机制

测试失败时的重试策略：

| 重试次数 | 策略 |
|----------|------|
| 第 1 次 | 将测试失败信息 + 完整错误输出反馈给 LLM，要求修正 |
| 第 2 次 | 同上，但附加强调"这是最后一次尝试" |
| 仍失败 | 停止自动修复 → 降级到人工审批 → 在 Issue 中附上失败原因和已生成的 diff |

## 修复后验证

PR 合并后的反馈闭环：

1. **GitHub Webhook** → 通知 Sentinel PR 已合并
2. Sentinel 更新 issue 状态为 `resolved`
3. 记录 `fix_history`：合并时间、diff 大小、测试结果
4. **持续监控**：如果相同 signature 在 24h 内再次出现 → issue 自动 reopen → 标记 `sentinel:regression`
5. **统计更新**：更新 MTTR、自动修复成功率等 Dashboard 指标

## 回滚机制

如果自动修复引入了新问题：

1. **人工发现** → 在 PR 页面直接 revert
2. **自动发现** → 相同错误再次触发 → 自动 reopen issue → 通知团队
3. **Dashboard 操作** → 在 Issue 详情页点击「标记回滚」，Sentinel 会自动创建 revert PR

## 降级场景汇总

| 场景 | 降级后行为 |
|------|-----------|
| 路径在黑名单 | 推送到审批队列，附安全拦截原因 |
| AI 评估不可修复 | 推送到审批队列，附 AI 分析 |
| 变更范围过大 | 推送到审批队列，附 diff 预览 |
| 测试失败 (2 次重试后) | 推送到审批队列，附失败日志和 diff |
| PR 创建失败 | 更新 issue，通知人工介入 |

## 日志与审计

每次自动修复操作都会记录完整审计日志：

- `issue_timeline` 表：记录每一步的时间戳和结果
- `fix_history` 表：记录完整的修复详情
- MinIO：保存完整的 diff 文件
- 平台日志：记录详细的执行日志用于排查
